## Project Overview

This project is a Laravel web application for managing medical appointments. It has three main user roles:

- Admin: manages users, doctors, specialties, and appointments.
- Doctor: manages professional profile, availability slots, and appointment requests.
- Patient: browses doctors, books appointments, manages appointments, and reads notifications.

In simple exam terms, the application receives a request from the browser, sends it to a route, executes controller logic, reads or writes database records through Eloquent models, and returns a Blade view as the response.

## Technologies Used

- PHP 8.2 or higher: backend programming language.
- Laravel 12: main web framework.
- Laravel Breeze: authentication scaffolding for login, registration, password reset, email verification, and profile screens.
- Eloquent ORM: database access layer using models such as `User`, `Doctor`, `Availability`, and `Appointment`.
- Blade: Laravel templating engine used for HTML views.
- SQLite database: local database file exists at `database/database.sqlite`; other databases can be configured through `.env`.
- Vite: frontend asset bundler.
- Tailwind CSS: utility-first CSS framework used by the Blade interface.
- Alpine.js: lightweight JavaScript behavior for UI components.
- PHPUnit: automated testing framework.
- Composer: PHP dependency manager.
- npm: JavaScript dependency manager.

## Project Architecture

The project follows the Laravel MVC pattern:

- Model: represents application data and business relationships. Example: `Appointment` represents a medical appointment.
- View: displays HTML pages to the user. Example: `resources/views/patient/appointments/index.blade.php`.
- Controller: receives a request, coordinates models, and returns a view or redirect. Example: `Patient/AppointmentController`.

The project also uses common Laravel supporting layers:

- Routes: map URLs to controllers.
- Middleware: checks authentication and role permissions before the controller runs.
- Form Requests: validate input before saving data.
- Policies: centralize authorization rules for sensitive actions.
- Mail and Notifications: send appointment status messages to patients.
- Migrations, factories, and seeders: define and populate the database.

- `artisan`: Laravel command-line entry point. It runs commands such as `php artisan migrate`, `php artisan serve`, and custom commands like `appointments:expire`.
- `composer.json`: PHP dependency and script definition file. It requires Laravel 12 and development tools such as Breeze, Pint, Sail, and PHPUnit.

### `app/`

The `app` folder contains the main Laravel application code. In MVC terms, this is where most models, controllers, middleware, policies, mail classes, notifications, and providers live.

#### `app/Console/Commands/ExpireAppointments.php`

This custom Artisan command expires old appointments. Its signature is `appointments:expire`.

- Purpose: automatically updates appointments whose scheduled time has passed.
- Important method: `handle()`.
- Main rules:
  - `pending` appointments in the past become `cancelled`.
  - `accepted` appointments in the past become `missed`.
  - Cancelled pending slots are released by setting the related availability back to available.
- Interaction: uses `Appointment` scopes and sends `AppointmentExpiredNotification` to patients.

#### `app/Http/Controllers/`

Controllers are the C in MVC. They receive requests from routes, call models, validate actions, and return views or redirects.

- `Controller.php`: Base abstract controller class. Other controllers extend it.
- `AppointmentController.php`: A general appointment controller outside role-specific folders. It lists appointments and updates or deletes an appointment. The role-specific appointment controllers are more important in the current route structure.
- `ProfileController.php`: Breeze-style general profile controller for editing, updating, and deleting a user account.

##### Admin Controllers

- `Admin/AppointmentController.php`: Admin appointment management. Important methods: `index`, `show`, `cancel`, `updateStatus`. It lists all appointments, filters by status/search, displays details, cancels appointments, and changes status.
- `Admin/DashboardController.php`: Builds admin dashboard statistics. It counts patients, doctors, appointments, appointments by status, today appointments, and recent appointments.
- `Admin/DoctorController.php`: Admin CRUD for doctor records. Important methods: `index`, `create`, `store`, `edit`, `update`, `destroy`. It connects a `User` with role doctor to a `Doctor` professional profile and specialty.
- `Admin/ProfileController.php`: Lets an admin edit account details and profile image.
- `Admin/SpecialtyController.php`: Admin CRUD for medical specialties. It uses `Speciality` model and store/update request classes.
- `Admin/UserController.php`: Admin CRUD for users. It creates and updates users, roles, and account data.

##### Auth Controllers

These controllers come from Laravel Breeze and implement authentication workflows.

- `Auth/AuthenticatedSessionController.php`: Login and logout. Important methods: `create`, `store`, `destroy`, and `dashboardRouteFor`. After login it redirects users to the correct dashboard based on role.
- `Auth/ConfirmablePasswordController.php`: Password confirmation screen and confirmation handling.
- `Auth/EmailVerificationNotificationController.php`: Resends verification email notifications.
- `Auth/EmailVerificationPromptController.php`: Shows the email verification prompt.
- `Auth/NewPasswordController.php`: Displays and processes password reset form.
- `Auth/PasswordController.php`: Updates the authenticated user's password.
- `Auth/PasswordResetLinkController.php`: Sends password reset links.
- `Auth/RegisteredUserController.php`: Registration. It creates users and redirects them according to role.
- `Auth/VerifyEmailController.php`: Verifies user email using signed verification links.

##### Doctor Controllers

- `Doctor/AppointmentController.php`: Lets doctors view appointment requests, accept, reject, complete, delete, or reschedule appointments. It uses transactions when appointment status and availability must change together.
- `Doctor/AvailabilityController.php`: Lets doctors create and delete availability slots. It supports creating one slot or generating many slots from a time range and duration.
- `Doctor/DashboardController.php`: Prepares doctor dashboard data: appointment totals, pending requests, accepted appointments, and upcoming appointments.
- `Doctor/ProfileController.php`: Lets doctors update their personal image and professional data such as phone, address, bio, and specialty.

##### Patient Controllers

- `Patient/AppointmentController.php`: Patient appointment workflow. Important methods: `index`, `create`, `store`, `show`, `edit`, `update`, `destroy`. It books an appointment by selecting a doctor and available slot, marks the slot unavailable, and allows cancellation.
- `Patient/DashboardController.php`: Shows patient dashboard data such as upcoming appointments and appointment statistics.
- `Patient/DoctorController.php`: Doctor directory for patients. It supports search and specialty filtering, and displays doctor details with availability.
- `Patient/NotificationController.php`: Lists patient notifications and marks one or all notifications as read.
- `Patient/ProfileController.php`: Lets patients update account information and profile image.

#### `app/Http/Middleware/`

Middleware runs before the controller. It is useful for security checks.

- `AdminMiddleware.php`: Allows access only if the authenticated user's role is `admin`.
- `DoctorMiddleware.php`: Allows access only if the authenticated user's role is `doctor`.
- `PatientMiddleware.php`: Allows access only if the authenticated user's role is `patient`.
- `RoleMiddleware.php`: Generic role checker that can accept one or more allowed roles. It is useful when a route can be shared by several roles.

These middleware aliases are registered in `bootstrap/app.php`.

#### `app/Http/Requests/`

Form Request classes keep validation logic out of controllers. This makes controllers cleaner.

- `Auth/LoginRequest.php`: Validates login email and password, performs authentication, and applies rate limiting.
- `ProfileUpdateRequest.php`: Validates profile name and email, ensuring email uniqueness except for the current user.
- `StoreAppointmentRequest.php`: Validates appointment booking. It checks that the doctor exists and the selected availability exists, belongs to that doctor, is available, and is not in the past.
- `UpdateAppointmentRequest.php`: Validates appointment status changes and patient note updates. It applies different allowed fields depending on the user's role.
- `StoreDoctorRequest.php`: Validates doctor creation, including user, specialty, phone, address, bio, and optional image.
- `UpdateDoctorRequest.php`: Validates doctor updates and optional specialty/image changes.
- `StoreSpecialtyRequest.php`: Validates new specialty name and description.
- `UpdateSpecialtyRequest.php`: Validates specialty updates, ignoring the current specialty when checking unique name.

#### `app/Mail/`

Mail classes describe emails sent by the application.

- `AppointmentCancelled.php`: Email for cancelled appointments.
- `AppointmentConfirmed.php`: Email for confirmed appointments.
- `AppointmentExpired.php`: Email for appointments expired by the scheduled command.
- `AppointmentRefused.php`: Email for rejected appointments.
- `AppointmentRescheduled.php`: Email for rescheduled appointments.

Each mail class usually receives an `Appointment` object, defines the email subject in `envelope()`, and selects a Blade email template in `content()`.

#### `app/Models/`

Models are the M in MVC. They represent database tables and define relationships.

- `User.php`: Represents users. Important fields include `name`, `email`, `password`, `role`, and `profile_image`. Important methods: `doctor()`, `appointments()`, `scopePatients()`, `scopeDoctors()`, `scopeAdmins()`, `isAdmin()`, `isDoctor()`, `isPatient()`, and `getProfileImageUrlAttribute()`.
- `Doctor.php`: Represents professional doctor profiles. It belongs to a `User` and a `Speciality`, and has many `Availability` and `Appointment` records.
- `Speciality.php`: Represents a medical specialty such as cardiology. It has many doctors.
- `Availability.php`: Represents a doctor's available time slot. Important scopes: `available()`, `byDoctor()`, `byDate()`, `byDateRange()`.
- `Appointment.php`: Represents a patient booking. It belongs to a patient `User`, a `Doctor`, and an `Availability`. Important scopes: `pending()`, `accepted()`, `rejected()`, `cancelled()`, `completed()`, `missed()`, `upcoming()`, `past()`.
- `Admin.php`: A simple model placeholder for admin-related data. In the current app, admin users are mainly represented by `User` records with role `admin`.

#### `app/Notifications/`

Notifications can be stored in the database and sent by email.

- `AppointmentExpiredNotification.php`: Notifies a patient when an appointment is expired and changed to cancelled or missed.
- `AppointmentRescheduledNotification.php`: Notifies a patient when an appointment has been rescheduled.

#### `app/Policies/AppointmentPolicy.php`

Policies define authorization rules. `AppointmentPolicy` checks whether a user can view, update, or delete an appointment.

- Admins can manage appointments broadly.
- Doctors can manage appointments assigned to their doctor profile.
- Patients can manage their own appointments.

#### `app/Providers/AppServiceProvider.php`

Registers application services and boot logic. In this project it also customizes redirection after authentication so users are sent to the correct dashboard for their role.

#### `app/View/Components/`

- `AppLayout.php`: Backing class for authenticated app layout component.
- `GuestLayout.php`: Backing class for guest/auth pages such as login and register.

### `bootstrap/`

- `bootstrap/app.php`: Laravel 12 application bootstrap file. It configures routing, health route `/up`, middleware aliases, and exception handling.
- `bootstrap/providers.php`: Lists service providers loaded by Laravel.
- `bootstrap/cache/`: Generated optimized framework cache files. It exists for performance and is normally not edited manually.

### `config/`

Configuration files read values from `.env` and tell Laravel how services should behave.

- `app.php`: App name, environment, debug mode, URL, locale, key, and providers.
- `auth.php`: Authentication guards, user providers, password reset settings.
- `cache.php`: Cache store configuration.
- `database.php`: Database connections such as SQLite or MySQL.
- `filesystems.php`: Local/public disk configuration, used for profile images and uploaded files.
- `logging.php`: Log channels and log levels.
- `mail.php`: Mail transport configuration used by mail and notifications.
- `queue.php`: Queue connection configuration for jobs.
- `services.php`: Credentials for third-party services.
- `session.php`: Session driver, cookie, lifetime, and security options.

### `database/`

The `database` folder defines and populates the application's data.

#### Factories

Factories create fake data for tests and seeders.

- `UserFactory.php`: Generates users and includes states for patient, doctor, and admin roles.
- `DoctorFactory.php`: Generates doctor profile data.
- `SpecialityFactory.php`: Generates medical specialties.
- `AvailabilityFactory.php`: Generates doctor availability slots.
- `AppointmentFactory.php`: Generates appointments and includes states such as pending, accepted, rejected, cancelled, completed, and missed.

#### Migrations

Migrations define the database schema.

- `0001_01_01_000000_create_users_table.php`: Creates `users`, `password_reset_tokens`, and `sessions`. The `users` table includes `role` with values `patient`, `doctor`, and `admin`.
- `0001_01_01_000001_create_cache_table.php`: Creates database cache tables.
- `0001_01_01_000002_create_jobs_table.php`: Creates queue job, job batch, and failed job tables.
- `2026_06_06_144514_create_specialities_table.php`: Creates `specialities` with unique name and optional description.
- `2026_06_06_144525_create_doctors_table.php`: Creates `doctors`, connecting a doctor profile to a user and specialty. It stores phone, address, bio, and photo.
- `2026_06_06_144545_create_availabilities_table.php`: Creates `availabilities`, including doctor, date, start time, end time, and `is_available`.
- `2026_06_06_144600_create_appointments_table.php`: Creates `appointments`, connecting patient, doctor, and availability. It stores appointment date, status, and notes.
- `2026_06_07_004927_create_notifications_table.php`: Creates Laravel's `notifications` table for database notifications.
- `2026_06_07_010741_add_profile_image_to_users_table.php`: Adds `profile_image` to users.

#### Seeders

Seeders insert sample data.

- `DatabaseSeeder.php`: Main seeder that calls the other seeders in order.
- `UserSeeder.php`: Creates initial users, including admin, patients, and doctor-role users.
- `SpecialitySeeder.php`: Creates medical specialties.
- `DoctorSeeder.php`: Creates doctor profiles connected to doctor users and specialties.
- `AvailabilitySeeder.php`: Creates appointment slots for doctors.
- `AppointmentSeeder.php`: Creates sample appointments.

Other files:

- `.gitignore`: Keeps generated database files controlled appropriately.
- `database.sqlite`: Local SQLite database used for development/testing when configured.

## Laravel-Specific Parts

### Controllers

Controllers are grouped by role:

- Admin controllers manage global system data.
- Doctor controllers manage doctor-specific data.
- Patient controllers manage patient-specific workflows.
- Auth controllers handle authentication.

This role-based controller organization makes the project easier to understand because each folder matches a real user type.

### Models and Relationships

Main relationships:

- `User` has one `Doctor` profile when role is doctor.
- `User` has many `Appointment` records as a patient.
- `Doctor` belongs to `User`.
- `Doctor` belongs to `Speciality`.
- `Doctor` has many `Availability` records.
- `Doctor` has many `Appointment` records.
- `Availability` belongs to `Doctor`.
- `Availability` has many `Appointment` records.
- `Appointment` belongs to patient `User`, `Doctor`, and `Availability`.

### Routes and Middleware

Routes are protected like this:

- Admin routes: `auth` plus `admin`.
- Patient routes: `auth` plus `patient`.
- Doctor routes: `auth` plus `doctor`.

This means the user must be logged in first, then must have the correct role.

### Form Requests

Form Requests protect the database from invalid input. For example, a patient cannot book an appointment using an unavailable slot because `StoreAppointmentRequest` checks the availability record before the controller creates the appointment.

### Blade Views

Blade views are separated by role. This mirrors the route/controller structure:

- `resources/views/admin`
- `resources/views/doctor`
- `resources/views/patient`
- `resources/views/auth`

This is a clean Laravel pattern because UI files are organized around features and users.

## Authentication and Authorization

Authentication answers: "Who are you?"  
Authorization answers: "What are you allowed to do?"

This project uses Laravel Breeze for authentication:

1. A guest visits `/login`.
2. `AuthenticatedSessionController@store` receives the login form.
3. `LoginRequest` validates credentials and rate limits failed attempts.
4. Laravel creates an authenticated session.
5. The app redirects the user based on role:
   - Admin to `admin.dashboard`
   - Doctor to `doctor.dashboard`
   - Patient to `patient.dashboard`

Role authorization is handled by middleware:

- `AdminMiddleware`
- `DoctorMiddleware`
- `PatientMiddleware`
- `RoleMiddleware`

Appointment authorization is also supported by `AppointmentPolicy`, which checks whether the current user owns or is responsible for the appointment.

## Database and Data Flow

### Main Tables

- `users`: stores account data and role.
- `specialities`: stores medical specialty names and descriptions.
- `doctors`: stores doctor professional profile data.
- `availabilities`: stores time slots created by doctors.
- `appointments`: stores patient bookings.
- `notifications`: stores database notifications.
- `sessions`, `password_reset_tokens`, `cache`, `jobs`: Laravel infrastructure tables.

### Appointment Booking Flow

1. Patient opens the doctor directory.
2. Patient selects a doctor.
3. The app shows available future slots from `availabilities`.
4. Patient submits booking form.
5. `StoreAppointmentRequest` validates doctor and slot.
6. `Patient/AppointmentController@store` creates an `Appointment`.
7. The selected `Availability` is marked unavailable.
8. Patient is redirected with a success message.
9. Doctor sees the appointment request in their dashboard or appointments list.

### Appointment Status Flow

1. Doctor opens appointment request.
2. Doctor accepts, rejects, completes, or reschedules it.
3. `Doctor/AppointmentController` updates appointment status.
4. Related availability is updated when needed.
5. Mail and notification classes can inform the patient.

### Expiration Flow

1. Scheduler or developer runs `php artisan appointments:expire`.
2. The command finds old pending and accepted appointments.
3. Old pending appointments become cancelled.
4. Old accepted appointments become missed.
5. Patients receive expiration notifications.

## Conclusion

This Laravel project is a complete MVC medical appointment booking platform. It separates responsibilities clearly:

- Models represent the database and relationships.
- Controllers process requests for each role.
- Views display role-specific pages.
- Middleware protects routes.
- Form Requests validate input.
- Migrations define the database.

For an exam, the most important idea is the request lifecycle: browser request -> route -> middleware -> controller -> model/database -> Blade view or redirect. The project applies this lifecycle consistently for admins, doctors, and patients.
